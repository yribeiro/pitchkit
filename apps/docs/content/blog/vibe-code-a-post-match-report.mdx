This is the report we're going to build. It covers the Euro 2024 final from StatsBomb's free
event data, and the whole thing is one HTML file:

![The top of the finished report: score, scorers with the xG of each goal, and the key numbers for Spain and England](/blog/vibe-code-a-post-match-report/report-top.webp)

[Open the finished report](/blog/vibe-code-a-post-match-report/euro-2024-final-report.html) (950 KB). Hover the shots for the player, minute and xG.

A coding agent wrote all of it from six prompts. You don't type any code. You do read what the
agent says back after each prompt, and that turns out to matter, because both of our test runs
went wrong somewhere in a way the agent only noticed when it was told to look.

Below are the prompts in the order you send them, with notes on why each one says what it says.
They're written for Claude Code. Codex needs two changes, which are shown where they come up.

## What you need

- [Node.js](https://nodejs.org) 22 or newer.
- Claude Code or Codex, with a plan or API credits. A full run from an empty folder took about
  ten minutes of agent time.
- A terminal (Terminal on a Mac, or WSL on Windows) and an empty folder.

## 1. Set up the project

<Tabs items={["Claude Code", "Codex"]}>
<Tab value="Claude Code">

```text
I'm a football analyst. I want to build a post-match report for the Euro 2024
final, Spain v England (StatsBomb open data, match id 3943043), and share it as
a single HTML file.

Set up a project in this empty folder:

- Vite + React + TypeScript.
- Install @pitchkit/react, @pitchkit/core and @pitchkit/data-providers. Then run
  `npx @pitchkit/react skills install` and read the skill it installs before
  writing any PitchKit code. PitchKit is new and is probably not in your
  training data, so don't guess its API: if the skill doesn't cover something,
  read https://www.pitchkitjs.com/llms.txt.
- The build must produce ONE self-contained HTML file (use
  vite-plugin-singlefile) that opens with a double click: no server, and no
  network requests when someone opens it. The PitchKit data loaders fetch from
  GitHub, so we'll fetch the data once, save it in the project and bundle it
  into the page (that's the next step).

Write a short project brief to CLAUDE.md covering the goal, the match, the stack
and the single-file rule, so the next session starts with it. Don't build the
report yet.
```

</Tab>

PitchKit is the charting library here, and it's young enough that no model has learned it. Ask
an agent for a shot map without help and it tends to write mplsoccer's Python API in JSX, using
components that don't exist. `skills install` copies PitchKit's own instructions for agents into
the project, matched to the version you installed. Claude Code looks for them in `.claude/skills`
and Codex in `.agents/skills`, which is the only reason the two prompts differ, apart from the
name of the brief file.

The single-file rule comes first because it changes how everything else is built. PitchKit's
data loaders fetch from GitHub when the page opens, and a report that does that breaks the moment
someone opens it on a train. The skill's own data example fetches live, so unless the prompt
says otherwise, that's what the agent copies.

## 2. Get the data, and look at it

```text
Now the data. Write scripts/fetch-match.ts using
@pitchkit/data-providers/statsbomb to fetch the match record (competition 55,
season 282), the lineups and the events for match 3943043. Save them to
src/data/match.json. Keep shots, passes, cards, substitutions, the lineups and
anything you'd need for a momentum chart; drop the rest. Add it as an npm script
and run it.

Then, without writing any UI, tell me what's in the data: the score, the
goalscorers and their minutes, shots and xG per team, and any traps you noticed
(periods, stoppage time, penalties, own goals, player names). Check these
against the raw events rather than what you remember of the match.
```

Read this reply properly. You should get back:

|       | Spain                                  | England         |
| ----- | -------------------------------------- | --------------- |
| Goals | Nico Williams 47', Mikel Oyarzabal 86' | Cole Palmer 73' |
| Shots | 16                                     | 9               |
| xG    | 1.79                                   | 0.73            |

If your numbers are different, sort it out now. It's a lot easier than finding out from a
finished page.

The agent has read plenty about this match, and the last line of the prompt is there to stop it
filling gaps from memory. Our runs also turned up the traps you'd hope an analyst would spot.
StatsBomb counts stoppage time inside the minute, so the first half runs to 47' and the second
half starts again at 45'. Williams' goal is in the second half even though 47' happened twice.
Players are listed under their full legal names, so without being told the agent will write
"Nicholas Williams Arthuer" in the header. The data has a `player_nickname` field for this.

## 3. Plan the report

```text
Plan the report before writing it. The reader is a head coach on a laptop the
morning after the game. Top to bottom:

1. Header: teams, score, scorers, competition, stage, date, venue.
2. Key numbers, side by side: goals, xG, shots, shots on target, passes, pass
   completion, share of passes.
3. An xG race chart across the match, with goals marked.
4. A match momentum chart with goals and cards.
5. A shot map per team: marker size by xG, goals highlighted, a tooltip with
   player, minute and xG.
6. A pass network per team: its starting XI, up to that team's own first
   substitution.
7. Three takeaways in plain English, each one backed by a number on the page.

Tell me which PitchKit component each section uses and exactly how every number
is computed. Don't write code yet; wait for my OK.
```

Change the list to suit your own reader, but keep the last paragraph. Asking how each number is
worked out is how you find the decisions the agent would otherwise make quietly. StatsBomb's
open data doesn't include possession, for example, so an agent asked for possession will invent
a formula for it. Share of passes is what we can actually count, so that's what the prompt asks
for.

The pass network line has a catch in this match. Rodri went off injured at half-time, so
Spain's network only covers the first half while England's runs to Kane's substitution on 61'.
The plan in our second run pointed this out before writing any code. We kept it, and the
finished page says the two windows are different lengths.

If the plan mentions a `<ShotMap>` or `<PassNetwork>` component, stop there. PitchKit doesn't
have either. A shot map is a pitch with a scatter layer on it, and seeing those names means the
agent didn't read the skill.

## 4. Build it

```text
Looks good, build it. Every number on the page must be calculated from
src/data/match.json, including the numbers inside the takeaways: write the
sentences yourself, but don't type any figure into them. Nothing from memory.

When it's built, run the type checker and the build, then open dist/index.html
in a headless browser at laptop width (1280px), take a screenshot and look at
it. Check every section shows sensible numbers and nothing is cut off or blank.
Fix anything wrong before you stop.
```

The screenshot is the line to keep. In the first test run we only asked for the type checker and
the build. Both passed, and the passes row on the page read 0, with a completion rate of NaN%.
The data was fine, but the code was reading a field that wasn't there. The same screenshot
showed the xG chart stopping at 90' while the match ran to 94', and labels you couldn't read on
the dark background. A passing build only tells you the code runs. Looking at the page is how
you find out whether it's right.

When it's done, open `dist/index.html` from your file manager. It won't look like much yet.

## 5. Make it look finished

```text
Now make it look like a finished piece of analysis: minimal, clean, data first.
Use the PitchKit brand:

- Dark page #0a0a0a, cards #121212 with a 1px #262626 border, 12px radius.
- Text #fafafa, secondary text #a3a3a3. System UI font, tabular numbers for
  every stat.
- Spain in PitchKit's emerald #34d399, England in #38bdf8. On the shot maps,
  goals are #fb923c.
- Pitches: surface #0b1712, lines rgba(255,255,255,0.32), no stripes.
- A single centred column, max 1040px wide, generous spacing, no gradients, no
  shadows, no emoji. Section titles small and uppercase; let the charts carry
  the page.
- Footer: "Built with PitchKit" and "Data: StatsBomb open data".

Theme PitchKit through its CSS variables only, including the chart variables, so
the axes, grid and labels read properly on a dark page. Then screenshot it at
375px wide and go through it section by section, including the names and numbers
on the pass networks. Fix anything that doesn't read well on a phone, and
rebuild when you're done.
```

Left to describe "clean" on its own, an agent will choose its own colours. Give it the hex values.
These are PitchKit's. Use your club's instead if you like, as long as the two teams are easy to
tell apart and goals get a third colour neither team uses.

Phones were where this step earned its keep. At 375px the pass networks turned into a pile of
overlapping circles, because the nodes keep the same pixel size while the pitch shrinks. The
agent made the nodes smaller on narrow screens, hid the names on the pitch and put a shirt
number key underneath. It also found that the shirt numbers had disappeared on desktop. They
take their colour from the pitch lines, which this brand dims to a third. Neither problem shows
up unless someone looks.

## 6. Check it before you send it

```text
Review the report as if you were the analyst about to send it. Rebuild, then:

- Write a separate script that re-derives every number on the page from the raw
  StatsBomb events, without using the report's code, and compares it with the
  text of the built page. List anything that doesn't match.
- Open dist/index.html in a headless browser with the network blocked and
  confirm it makes no requests and still renders everything.
- Read the takeaways again and confirm each one only claims what the numbers on
  the page show.

Fix whatever is wrong, then give me the final file size and a one-paragraph
summary I can paste into an email with the report attached. Only quote figures
the check confirmed.
```

The checking script mustn't share code with the report, otherwise a bug in one can hide behind
the same bug in the other. In our second run it compared 50 figures and names with the
finished page and found nothing wrong.

The takeaways were another matter. Both runs had overclaimed. One said "Spain had the ball",
which is a claim about possession, on a page that only measures passes. The first run said
"the goals didn't follow the chances" about a game the side with 2.5 times the xG won. Both got
rewritten at this step. Read the takeaways yourself anyway. They're the part a coach will quote
back to you.

## Sending it

`dist/index.html` is the report. It has the data and the charts inside it, so it works without
an internet connection and anyone can open it in a browser.

How you send it matters more than you'd think. Some company email systems block `.html`
attachments, and a phone's attachment preview often won't run the page's code, so the
recipient sees a blank screen. Put the file in a shared drive or a Teams or Slack channel, and
tell people to download it and open it in Chrome, Safari or Edge. Do a test send to yourself
first.
