This is the deck we're going to build. It's a post-match report on the Euro 2024 final, made from
StatsBomb's free event data, and the whole thing is one HTML file. Click into it and use your arrow
keys, or the arrows underneath the slides.

A coding agent wrote all of it from six prompts. You don't type any code, but you do have to read
what the agent says back. Every one of our test runs went wrong somewhere, and each time the agent
only noticed once it was told to look.

Below are the prompts, in order, and why each is worded the way it is. They're written for Claude
Code. For Codex, the first prompt changes in two places, shown in its tab.

## What you need

- [Node.js](https://nodejs.org) 22 or newer.
- Claude Code or Codex, with a plan or API credits. Our runs from an empty folder took between ten
  and twenty minutes of agent time.
- A terminal: Terminal on a Mac, or [WSL](https://learn.microsoft.com/windows/wsl/install) on
  Windows.

Both tools ask you to sign in the first time they start. If `npm install -g` fails with a
permissions error on a Mac, each tool's install page has an installer that avoids it.

Send each prompt as a separate message and wait for the agent to finish before sending the next. It
will ask permission to install packages and run scripts, and at step 4 to download a headless
browser (a copy of Chrome it can drive to take screenshots, a couple of hundred MB). All of that is
expected, so allow it. If a step fails, paste the error back and ask it to fix it.

## 1. Set up the project

<Tabs items={["Claude Code", "Codex"]}>
<Tab value="Claude Code">

```text
I'm a football analyst. I want to build a post-match report for the Euro 2024
final, Spain v England (StatsBomb open data, match id 3943043), as a slide pack
I can send as a single HTML file.

Set up a project in this empty folder:

- Vite + React + TypeScript.
- Install @pitchkit/react, @pitchkit/core and @pitchkit/data-providers. Then run
  `npx @pitchkit/react skills install` and read the skill it installs before
  writing any PitchKit code. PitchKit is new and is probably not in your
  training data, so don't guess its API: if the skill doesn't cover something,
  read https://www.pitchkitjs.com/llms.txt.
- The build must produce ONE self-contained HTML file (use
  vite-plugin-singlefile) that opens with a double click: no server, and no
  network requests when someone opens it. Remove anything from the starter
  template that would load from outside the file. The PitchKit data loaders
  fetch from GitHub, so we'll fetch the data once, save it in the project and
  bundle it into the page (that's the next step).

Write a short project brief to CLAUDE.md covering the goal, the match, the stack
and the single-file rule, so the next session starts with it. Don't build the
report yet.
```

</Tab>

PitchKit is the charting library here, and it's young enough that no model has learned it. Ask an
agent for a shot map without help and it tends to write mplsoccer's Python API in JSX, using
components that don't exist. `skills install` copies PitchKit's own instructions for agents into the
project, matched to the version you installed. Claude Code looks for them in `.claude/skills` and
Codex in `.agents/skills`, which is the only reason the two prompts differ, apart from the name of
the brief file.

The single-file rule is in the first prompt because otherwise the agent builds the deck around a
live fetch. PitchKit's data loaders fetch from GitHub when the page opens, and a report that does
that breaks the moment someone opens it on a train. The skill's own data example fetches live, so
unless the prompt says otherwise, that's what the agent copies. The line about the starter template
is there because every run tripped on the same thing: Vite's template links a favicon that isn't in
the file.

## 2. Get the data, and look at it

```text
Now the data. Write scripts/fetch-match.ts using
@pitchkit/data-providers/statsbomb to fetch the match record (competition 55,
season 282), the lineups and the events for match 3943043. Save them to
src/data/match.json. Keep shots, passes, cards, substitutions, the lineups and
anything you'd need for a momentum chart; drop the rest. Add it as an npm script
and run it.

Then, without writing any UI, tell me what's in the data: the score, the
goalscorers and their minutes, shots and xG per team, and any traps you noticed
(periods, stoppage time, penalties, own goals, player names). Check these
against the raw events rather than what you remember of the match.
```

Read this reply properly. You should get back:

|       | Spain                                  | England         |
| ----- | -------------------------------------- | --------------- |
| Goals | Nico Williams 47', Mikel Oyarzabal 86' | Cole Palmer 73' |
| Shots | 16                                     | 9               |
| xG    | 1.79                                   | 0.73            |

If your numbers are different, sort it out now. It's a lot easier than finding out from a finished
deck.

The agent has read plenty about this match, and the last line of the prompt is there to stop it
filling gaps from memory. Every run also flagged two traps. StatsBomb counts stoppage time inside
the minute and restarts the clock at 45' for the second half, so this match has two 47ths: one in
first-half stoppage time and one just after the restart. Williams scored in the second, and an agent
that sorts by minute alone can put his goal in the wrong half. Players are listed under their full
legal names, so without being told the agent will write "Nicholas Williams Arthuer" on the title
slide. The data has a `player_nickname` field for this.

## 3. Plan the deck

```text
Plan the report before writing it. It's a slide pack, one slide per section, for
a head coach on a laptop the morning after the game. In order:

1. Title slide: teams, score, scorers, competition, stage, date, venue.
2. Key numbers, side by side: goals, xG, shots, shots on target, passes, pass
   completion, share of passes.
3. An xG race chart across the match, with goals marked.
4. A match momentum chart with goals and cards.
5. A shot map per team: marker size by xG, goals highlighted, a tooltip with
   player, minute and xG.
6. A pass network per team: its starting XI, up to that team's own first
   substitution.
7. Three takeaways in plain English, each one backed by a number in the deck.

Tell me which PitchKit component each slide uses and exactly how every number is
computed. Don't write code yet; wait for my OK.
```

Both tools have a plan mode, but you don't need it here. Approving a plan in Claude Code starts the
build straight away, before you've sent the rules in prompt 4. "Wait for my OK" does the same job in
either tool.

Change the list to suit your own reader, but keep the last paragraph. It makes the agent say how
it's working out each number, instead of picking a method and not telling you. StatsBomb's open data
doesn't include possession, for example, so an agent asked for possession will invent a formula for
it. Share of passes is what we can actually count, so that's what the prompt asks for.

The pass network line has a catch in this match. Rodri went off injured at half-time, so Spain's
network only covers the first half while England's runs to Kane's substitution on 61'. The plans in
our runs pointed this out before writing any code. We kept it, and the finished slide says the two
windows are different lengths.

If the plan mentions a `<ShotMap>` or `<PassNetwork>` component, stop there. PitchKit doesn't have
either. A shot map is a pitch with a scatter layer on it, and seeing those names means the agent
didn't read the skill.

## 4. Build it

```text
Looks good, build it. Every number in the deck must be calculated from
src/data/match.json, including the numbers inside the headlines and takeaways.
Write the sentences yourself, but don't type any figure into them, and don't
make any claim the numbers don't show. Nothing from memory.

When it's built, run the type checker and the build, then open dist/index.html
in a headless browser at 1280×720, screenshot every slide and look at them.
Check every slide shows sensible numbers and nothing is cut off or blank. Fix
anything wrong before you stop.
```

The screenshots are the part to keep. In the first test run we only asked for the type checker and
the build. Both passed, and the passes row read 0, with a completion rate of NaN%. The data was
fine, but the code was reading a field that wasn't there. The same screenshot showed the xG chart
stopping at 90' while the match ran to 94', and labels you couldn't read on the dark background.

When it's done, open `dist/index.html` from your file manager. Don't judge the look yet. That's the
next step.

## 5. Make it look finished

```text
Now make it look like a finished piece of analysis: minimal, clean, data first.
Use the PitchKit brand:

- Page #0a0a0a. Slides #121212 with a 1px #262626 border and 12px radius.
- Text #fafafa, secondary text #a3a3a3. System UI font, tabular numbers for
  every stat.
- Spain in PitchKit's emerald #34d399, England in #38bdf8. On the shot maps,
  goals are #fb923c.
- Pitches: surface #0b1712, lines rgba(255,255,255,0.32), no stripes.
- Slides are 16:9, in a horizontal strip that snaps to one slide at a time. Move
  between them with the arrow keys, on-screen arrows or a swipe, and show a
  slide counter. On a phone, let each slide fill the screen width and grow
  taller than 16:9 so the charts stay readable.
- Each slide gets a headline that states its main finding, built from the
  computed numbers, then the chart. No gradients, no shadows, no emoji.
- The deck must also work embedded in an iframe on another page.
- On every slide: "Built with PitchKit" and "Data: StatsBomb open data".

Theme PitchKit through its CSS variables only, including the chart variables, so
the axes, grid and labels read properly on a dark page. Then screenshot every
slide at 1280×720 and at 375px wide and go through them one by one, including
the names and numbers on the pass networks. Fix anything that doesn't read well,
and rebuild when you're done.
```

Ask for "clean" without saying what that means and the agent picks the colours. Give it hex values.
These are PitchKit's. Use your club's instead if you like, as long as the two teams are easy to tell
apart and goals get a third colour neither team uses.

"A headline that states its main finding" is what turns a set of charts into a report. Without it
you get slides titled "xG race". With it, the slide says "Spain built 1.79 xG to England's 0.73",
and the coach doesn't have to read the chart to get the point.

Most of what this step fixed was in the pass networks. Ruiz and Morata had almost the same average
position, and so did Foden and Mainoo, so their circles sat on top of each other with the numbers
unreadable. The agent nudged the nodes apart and says so in the slide's footnote. On a phone,
Carvajal's name ran off the edge of the pitch. On the title slide, the scorers' names wrapped one
word per line. The chart labels came out smeared, because PitchKit draws a halo behind them that
defaults to white and has to be set for a dark page. Each of these showed up in the screenshots and
nowhere else.

## 6. Check it before you send it

```text
Review the deck as if you were the analyst about to send it. Rebuild, then:

- Write a separate script that re-derives every number in the deck from the raw
  StatsBomb events, without using the deck's code, and compares it with the
  built page, including chart labels and tooltips. List anything that doesn't
  match.
- Open dist/index.html in a headless browser with the network blocked and
  confirm it makes no requests and still renders every slide.
- Read the takeaways again and confirm each one only claims what the numbers in
  the deck show.

Fix whatever is wrong, then give me the final file size and a one-paragraph
summary I can paste into an email with the deck attached. Only quote figures the
check confirmed.
```

The checking script mustn't share code with the deck, otherwise a bug in one can hide behind the
same bug in the other. In the deck above it compared 41 figures with the finished slides and found
nothing wrong.

The takeaways were harder. Every run overclaimed somewhere. One said "the goals didn't follow the
chances", in a game won by the side with 2.5 times the xG. Another said "Spain had the ball", which
is a claim about possession, in a deck that only measures passes. The check caught that one and
changed it to "Spain had more of the ball", which is the same claim again.

So we sent one more prompt:

```text
Takeaway 2 says Spain 'had more of the ball'. The deck measures passes, not
possession, so that's a claim we can't back up. Reword it so it only says what
the passing numbers show, then rebuild and re-run the check.
```

It came back as "Spain made most of the passes at a higher completion rate", and the agent also
dropped a final-third figure that had wandered in from the momentum slide. That's the version above.
Read the takeaways yourself even after the check. They're the part a coach will quote back to you.

## Sending it

`dist/index.html` is the deck. It has the data and the charts inside it, so it works without an
internet connection and anyone can open it in a browser.

Some company email systems block `.html` attachments, and a phone's attachment preview often won't
run the page's code, so the recipient sees a blank screen. Put the file in a shared drive or a Teams
or Slack channel, and tell people to download it and open it in Chrome, Safari or Edge. Do a test
send to yourself first.
