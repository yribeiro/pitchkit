This is the report we're going to build: a nine-slide deck on the Euro 2024 final, made from
StatsBomb's free event data and saved as one HTML file you can send to a coach. It's a single page
where each screen is a slide. You scroll, or press the down arrow, to move on.

A coding agent writes all of it, from ten prompts, one slide at a time. You don't type any code, but
you do have to read what the agent says back. We ran this sequence several times from an empty
folder and rewrote the prompts after each run. Something went wrong on every run, and most of the
time the agent only caught it because the prompt told it to look.

Each screenshot below is the slide as the agent left it when that prompt finished. The prompts are
written for Claude Code, and Codex differs in the first one.

## What you need

- [Node.js](https://nodejs.org) 22 or newer.
- Claude Code or Codex, with a plan or API credits. The last full run took about 23 minutes of agent
  time. The longest steps were the first slides and the pass networks, at four or five minutes each.
- A terminal: Terminal on a Mac, or [WSL](https://learn.microsoft.com/windows/wsl/install) on
  Windows.

Both tools ask you to sign in the first time they start. If `npm install -g` fails with a

Send each prompt as a separate message and wait for the agent to finish before sending the next. It
will ask permission to install packages and run scripts, and to download a headless browser (a copy
of Chrome it can drive to take screenshots, a couple of hundred MB). That's all expected, so allow
it. If a step fails, paste the error back and ask it to fix it.

## 1. Set up the project


PitchKit is the charting library, and it's young enough that no model has learned it. Ask an agent
for a shot map without help and it tends to write mplsoccer's Python API in JSX, using components
that don't exist. `skills install` copies PitchKit's own instructions for agents into the project,
matched to the version you installed. Claude Code looks for them in `.claude/skills` and Codex in
`.agents/skills`, which is why the two prompts differ, along with the name of the brief file.

The single-file rule is in the first prompt because otherwise the agent builds the deck around a
live fetch. PitchKit's data loaders fetch from GitHub when the page opens, and a report that does
that breaks the moment someone opens it on a train. The skill's own data example fetches live, so
unless the prompt says otherwise, that's what the agent copies. The line about the starter template
is there because Vite's template links to a favicon and a few websites, and the agent found them
with a search for `http` in every run.

## 2. Build an empty scaffold

```text title="Prompt"
Now the empty scaffold: the deck, with no content in it yet. It should already look like a finished piece of analysis: minimal, clean and crisp, with the data doing the talking, in the PitchKit brand.

- Background #0a0a0a. Text #fafafa, secondary text #a3a3a3. Panels #121212 with a 1px #262626 border and 8px radius, used sparingly.
- Type: system UI font, four sizes at most. Headlines 32px on a laptop and 22px on a phone, weight 600, two lines at most. Body 16px. Labels and footnotes 13px, never smaller. Tabular numbers for every stat. Nothing heavier than weight 600.
- Spain #10b981 (PitchKit's emerald), England #3b82f6, goals #ea580c. These colours go on the data marks only. Team names and labels stay in the text colours, with a small coloured dot beside the name.
- Pitches: surface #0b1712, lines rgba(255,255,255,0.32), no stripes. Theme PitchKit through its CSS variables only, including every chart variable (axis, grid, text, and --pitch-chart-surface, which defaults to white), so the axes, grid and labels read properly on a dark page. Chart text such as axis ticks, legends and labels must be at least 12px; PitchKit draws some of it smaller, so enforce that in CSS.
- The chart fills the slide. Give it most of the height and keep the headline, footnote and footer small around it. Thin lines, generous margins, no gradients, no shadows, no emoji.
- It's one scrolling page that works like a slide deck. Each slide is a full-screen section, at least the full width and height of the screen. Scrolling, the down arrow, space or Page Down snaps to the next slide, and the up arrow or Page Up goes back. The slide is the screen, so no frames or boxes around it. Add a thin progress indicator at the edge, and a subtle "next" chevron on every slide but the last.
- On a phone (under 640px wide) the slides are still full width and a screen tall. A slide may run longer than the screen if it needs to.
- Every slide has a headline of ten words or fewer that states its main finding, a chart area, and a footer: "Built with PitchKit" and "Data: StatsBomb open data".
- The page must also work inside an iframe on another page, with each slide filling the frame.

For now, put one slide in it: the headline "Spain v England" and an empty PitchKit pitch. Then build, open dist/index.html in a headless browser, screenshot it at 1280×720, 960×540 and 375px wide, and look at all three. Fix anything wrong before you stop.
```

  caption="The scaffold: one slide, an empty pitch, and the PitchKit look."

Everything about the look goes in this prompt, before there's anything to look at. That way every
slide that follows comes out in the same style and you don't have a restyling pass at the end. Ask
for "clean" without saying what that means and the agent picks for you, and what it picks tends to
be heavy: our first decks had 52px bold headlines, 18 different text sizes and chart labels under
10px. So the prompt sets the type scale, a maximum weight and a minimum size, and says the chart
gets most of the slide.

The colours are PitchKit's emerald, its default blue and a darker orange for goals. We chose them
with a palette checker rather than by eye. The brighter green and sky blue we started with were too
light for a dark page, and to someone with tritan colour blindness Spain and England looked almost
the same. The rule that team colours go on the data and not on the text is for legibility: grey and
white text reads better than coloured text at small sizes. If you swap in your club's colours, check
them the same way.

The layout is in there too. Each slide is one full screen and the page snaps from one to the next,
so it reads like a deck without any slide software. The last line, about taking a screenshot and
looking at it, is in every prompt from here on. The first time through we asked only for a type
check and a build. Both passed, and the passes row on the page read 0, with a completion rate of
NaN%. This time the screenshots showed the empty pitch as a thin strip on a phone, so the agent
turned it vertical.

## 3. Get the data, and look at it

```text title="Prompt"
Now the data. Write scripts/fetch-match.ts using @pitchkit/data-providers/statsbomb to fetch the match record (competition 55, season 282), the lineups and the events for match 3943043. Save them to src/data/match.json. Keep every event that has a location, plus the substitutions, the cards, the lineups and the Half End events (the final whistle has no location); drop the rest. Add it as an npm script and run it.

Then, without changing the deck, tell me what's in the data: the score, the goalscorers and their minutes, shots and xG per team, and any traps you noticed (periods, stoppage time, penalties, own goals, player names). Check these against the raw events rather than what you remember of the match.
```

Read this reply properly. You should get back:

|       | Spain                                  | England         |
| ----- | -------------------------------------- | --------------- |
| Goals | Nico Williams 47', Mikel Oyarzabal 86' | Cole Palmer 73' |
| Shots | 16                                     | 9               |
| xG    | 1.79                                   | 0.73            |

If your numbers are different, sort it out now. It's a lot easier than finding out from a finished
slide.

The agent has read plenty about this match, and the last line of the prompt is there to stop it
filling gaps from memory. Every run also flagged the same two traps. StatsBomb's minute is elapsed
time, so Williams scores at 46:09 on its clock and the broadcast says 47'. And the clock restarts at
45' for the second half, so the minutes 45 to 47 exist twice, once in first-half stoppage time and
again after the restart. An agent that sorts by minute alone can put Williams' goal in the wrong
half.

Players are listed under their full legal names, so without being told the agent will write
"Nicholas Williams Arthuer" on the title slide. The lineups carry a `player_nickname` for each
player, which is where "Nico Williams" comes from. England's players mostly have none, so those
names fall back to the registered ones. The data has no penalties, own goals or shootout, and the
agent said so.

What you ask it to keep here decides what it can count later. The Half End events are in the list
because an earlier run left them out. The final whistle has no location, so "every event that has a
location" dropped it, and the last-15-minutes slide ended up a minute out until the check in step 10
caught it. "Every event with a location" keeps nearly all of them, so the saved file is about 2 MB,
which ends up inside the report.

## 4. The first slides

```text title="Prompt"
Now the first slides. Every number must be calculated from src/data/match.json, including the numbers in headlines: write the sentences yourself, but don't type any figure into them, and don't make a claim the numbers don't show. Nothing from memory. For every figure, tell me in a line how you worked it out.

Replace the placeholder slide with:

1. A title slide: teams, score, scorers with minutes (use nicknames), competition, stage, date, venue. Its headline should be a sentence about the result, not the scoreline repeated.
2. Key numbers, side by side: goals, xG, shots, shots on target (a goal counts as on target), passes, pass completion, share of passes (each side's passes over both sides' passes; that's not possession).
3. An xG race chart across the match, with goals marked and the scorers labelled.

Then build, open dist/index.html in a headless browser, screenshot every slide at 1280×720 and at 375px wide, and look at them. Check every slide shows sensible numbers and nothing is cut off or blank. Fix anything wrong before you stop.
```

The rule about numbers does most of the work in this prompt. Agents like to type `2–1` into a
headline, and from memory that's usually right, which is why it goes unnoticed on the day it's
wrong. Making it calculate every figure, and say how, is how you find the choices it made without
telling you. StatsBomb has no possession figure, for example, so an agent asked for possession will
make up a formula. Share of passes is something we can count, so the prompt asks for that and the
footnote says it isn't possession.

This was the longest step, at about five minutes, and the screenshots did most of it. The two-line
limit on headlines cut some of them off. PitchKit marks goals on the race chart in the team's
colour, so the agent drew its own orange markers. The scorers' labels collided with the lines, the
scorers' minutes wrapped on a phone, and the key numbers table overflowed at 960×540. PitchKit also
draws its chart text at 8.5 to 12px, under the 12px floor from step 2, so the agent set it to 13px.
Each one was fixed before the step finished.

## 5. Momentum

```text title="Prompt"
Add a match momentum slide after the xG race: bars for each minute, Spain up and England down, with goals and cards marked beneath. StatsBomb has no momentum figure, so derive one, and say in the slide's footnote that it's derived: for each minute, count each side's on-ball events in the attacking third (every event with a location and a player, except Pressure, which is off the ball), subtract England's from Spain's, and smooth over three minutes. Same rules on numbers, and the same build, screenshot and check as before.
```

<StageShot
  name="momentum"
  alt="Match momentum chart: green bars above the line for Spain and blue bars below for England, with goal and card markers underneath"
  caption="Slide 4, momentum. Derived from event data, not a StatsBomb figure."
/>

There's no agreed way to measure momentum, so a bare "add a momentum chart" gets whatever the agent
invents, and you'd have no way to know what the bars mean. The prompt gives it one line you can
defend: on-ball events in the attacking third, Spain minus England, smoothed. Pressure is excluded
because those events have a location and a player but happen off the ball, and an earlier run
counted them. The footnote on the slide repeats the method, so the coach reading the report knows
too.

The agent's first headline here, about the ball being near goal, claimed more than the bars show,
and it rewrote it to "Spain edged the attacking third in most minutes". The second half's bars
restart at 45, so the bars for 45 to 47 appear in both halves.

## 6. Shots

```text title="Prompt"
Add a shots slide: a shot map for each team, cropped to the attacking half, side by side on a laptop and stacked on a phone. Marker size follows xG, goals are highlighted, and each shot has a tooltip with the player, minute and xG: on hover on a laptop, and on a tap on a phone (if the library's tooltip doesn't open on tap, add a tap fallback). Same rules on numbers, and the same build, screenshot and check as before.
```

<StageShot
  name="shots"
  alt="Two shot maps cropped to the attacking half: Spain's 16 shots clustered in and around the box, England's 9 more spread out, goals in orange"
  caption="Slide 5, shots."
/>

On a laptop, hover over a shot and you get the player, minute and xG. A phone is trickier.
PitchKit's shot tooltip only listens for the mouse, and in the agent's tests it didn't open on a
tap, so it built a tap fallback. That's why the prompt asks for one. We've only tried it with
emulated taps, not on a real phone.

The agent's footnote first said each team was attacking upwards. PitchKit's vertical pitch puts
StatsBomb's attacking goal at the bottom, and the screenshot showed it, so the footnote now says so.
On a phone the stacked maps ran into the footnote, and the agent fixed the spacing.

The headline of each slide should say what happened in that window. Same rules on numbers, and the same build, screenshot and check as before.

"The last 15 minutes" can mean 76 to 90, or the last 15 up to the whistle. The prompt says up to the
whistle, stoppage time included, and asks for the window in a footnote so a reader can see which one
you got. The agent also checked both readings and found the same five shots in each.

## 8. Pass networks

```text title="Prompt"
Add a pass networks slide, one pitch per team, for its starting XI up to that team's own first substitution. Each player sits at the average spot of their passes made and passes received (made means attempted, received means completed). Node size is passes made plus received, and lines join pairs with 3 or more completed passes between them. Label each node with a shirt number and a name, and make sure no label overlaps another or runs off the pitch, on a phone as well. If two nodes would overlap, nudge them apart and say so in the footnote. Say in a footnote how long each team's window is. Same rules on numbers, and the same build, screenshot and check as before.
```

  name="passes"
  alt="Pass networks for Spain and England: circles at each starting player's average position, joined by lines, with shirt numbers and names"
  caption="Slide 8, pass networks. On a phone the two pitches stack, and the slide runs longer than the screen."

This was one of the harder slides. Rodri went off injured at half-time, so Spain's window is the
first 47 minutes, while England's runs to Kane's substitution on 61', 63 minutes in. The two windows
aren't the same length, so the slide compares completed passes per minute instead of totals.

The labels took the time. In the first version some sat on other players' circles, and "7 Morata"
read as if it belonged to Olmo. The agent wrote a label placer that tries eight positions at five
distances around each node, then checked it for overlaps at five screen widths. Foden and Mainoo had
almost the same average position, so their circles were nudged apart, and the footnote says so.

Read the headline here with a coach's eyes. "Spain completed passes at more than twice England's
rate" means passes per minute, 6.0 against 2.9, and the footnote says so. But slide 2 shows a
completion rate of 88% against 79%, and a reader could easily take "rate" to mean that. Nothing in
it is wrong, and the check passed it. It's still the kind of thing to send back with a one-line
prompt.

If the plan or the code mentions a `<ShotMap>` or `<PassNetwork>` component, stop there. PitchKit
doesn't have either. A pass network is a pitch with arrows and a scatter layer on it, and seeing
those names means the agent didn't read the skill.

## 9. The takeaways

```text title="Prompt"
Add a last slide with three takeaways in plain English. Each one must be backed by a number from the deck, with a note of which slide it comes from, and must only claim what that number shows. No takeaway may rely on a number that only appears in a tooltip. Same rules on numbers, and the same build, screenshot and check as before.
```

<StageShot
  name="takeaways"
  alt="Three takeaway cards: 1.79 v 0.73 xG, 6.0 v 2.9 completed passes a minute, and the winner at 86', each with the slide it comes from"
  caption="Slide 9, the takeaways, with the slide each number comes from."
/>

The takeaways are where overclaiming creeps in, since they're the only slide that's all sentences.
Across the runs we saw "the goals didn't follow the chances", in a game won by the side with 2.5
times the xG, and "Spain had the ball", which is a claim about possession in a deck that only
measures passes. Another run's first wording was "none from a shot worth more than 0.28 xG". The
biggest goal was worth 0.283, so it was quietly false, and the agent caught it on its own re-read.

The slide-reference line makes the agent show its working. Each takeaway points back to the slide it
comes from, so anyone can check a claim against it. The prompt also says no takeaway may rely on a
number that only appears in a tooltip, and this run's first draft broke that rule. Its third
takeaway leaned on the minutes of England's late shots, which you could only see by tapping them, so
the agent added them to the slide's footnote.

## 10. Check it before you send it

```text title="Prompt"
Review the deck as if you were the analyst about to send it. Rebuild, then:

- Write a separate script that re-derives every number in the deck from the raw StatsBomb events, without using the deck's code, and compares it with the built page, including chart labels and tooltips. List anything that doesn't match.
- Open dist/index.html in a headless browser with the network blocked and confirm it makes no requests and still renders every slide, at 1280×720, at 375px wide, and inside a 960×540 iframe, where every slide must fill the frame without being clipped. A slide may be taller than the frame if its maps need the height.
- Read the headlines and takeaways again and confirm each one only claims what the numbers in the deck show.

Fix whatever is wrong, then give me the final file size and a one-paragraph summary I can paste into an email with the deck attached. Only quote figures the check confirmed.
```

The checking script mustn't share code with the deck, otherwise a bug in one can hide behind the
same bug in the other. This run's script downloaded the raw StatsBomb files fresh and compared every
number, chart label and tooltip with the built page. It found two things wrong with the deck. Some
tooltips couldn't be reached because other marks sat on top of them, and the xG race headline said
the teams were level at the break, when the figures were 0.34 against 0.28. That one now says
"close".

It also found that the agent's own reply after step 5 had said Spain were ahead in 60 of 98 minutes.
The deck had the right figure, 59 of 97, because one minute was level. That's a mistake in the chat
rather than the report, and the kind you'd copy into an email without the check.

Earlier runs found more of the same. Tooltips showed StatsBomb's raw outcome `Off T`, a takeaway
cited a slide for a number that only appeared in a tooltip, and the final whistle went missing. The
words "including chart labels and tooltips" are what found most of them. Without them the script
would only read the text on the page.

The deck also has to work in a 960×540 frame, because this site shows the report in one. In this run
every slide filled the frame without being clipped.

Read the headlines and takeaways yourself even after the check. They're the part a coach will quote
back to you.

## What I'd change next time

The prompts above are the ones we ran, word for word. After this run, four things stand out:

- **Step 2: give one rule for all chart text.** PitchKit draws tooltips at 12px and some labels
  smaller, so "every other text, including chart ticks, legends, annotations and tooltips, is 13px"
  saves the agent a guess.
- **Steps 4 to 9: screenshot at 960×540 too.** The key numbers table overflowed at that size and was
  only caught because step 4's agent checked it anyway.
- **Step 2: goals are orange everywhere.** PitchKit draws its own goal markers in the team colour,
  so say "including PitchKit's own goal icons and markers".
- **Step 8: say what a rate is per.** "Completed passes per minute" in the prompt would have kept
  the headline from reading like a completion rate.
