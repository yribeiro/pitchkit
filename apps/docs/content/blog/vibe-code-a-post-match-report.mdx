This is the report we're going to build: a nine-slide deck on the Euro 2024 final, made from
StatsBomb's free event data and saved as one HTML file you can send to a coach. It's a single page
where each screen is a slide. You scroll, or press the down arrow, to move on.

A coding agent writes all of it, from ten prompts, one slide at a time. You don't type any code, but
you do have to read what the agent says back. We ran this sequence several times from an empty
folder and rewrote the prompts after each run. Something went wrong on every run, and most of the
time the agent only caught it because the prompt told it to look.

Each screenshot below is the slide as the agent left it when that prompt finished. The prompts are
written for Claude Code, and Codex differs in the first one.

## What you need

- [Node.js](https://nodejs.org) 22 or newer.
- Claude Code or Codex, with a plan or API credits. The last full run took about 20 minutes of agent
  time. The longest steps, at around four minutes each, were the pass networks and the final check.
- A terminal: Terminal on a Mac, or [WSL](https://learn.microsoft.com/windows/wsl/install) on
  Windows.

Both tools ask you to sign in the first time they start. If `npm install -g` fails with a
permissions error on a Mac, each tool's install page has an installer that avoids it.

Send each prompt as a separate message and wait for the agent to finish before sending the next. It
will ask permission to install packages and run scripts, and to download a headless browser (a copy
of Chrome it can drive to take screenshots, a couple of hundred MB). That's all expected, so allow
it. If a step fails, paste the error back and ask it to fix it.

## 1. Set up the project

<Tabs items={["Claude Code", "Codex"]}>
<Tab value="Claude Code">

```text title="Prompt"
I'm a football analyst. I want to build a post-match report for the Euro 2024 final, Spain v England (StatsBomb open data, match id 3943043), as a deck of full-screen slides that you scroll through, sent as a single HTML file. We'll build it one slide at a time.

Set up a project in this empty folder:

- Vite + React + TypeScript.
- Install @pitchkit/react, @pitchkit/core and @pitchkit/data-providers. Then run `npx @pitchkit/react skills install` and read the skill it installs before writing any PitchKit code. PitchKit is new and is probably not in your training data, so don't guess its API: if the skill doesn't cover something, read https://www.pitchkitjs.com/llms.txt.
- The build must produce ONE self-contained HTML file (use vite-plugin-singlefile) that opens with a double click: no server, and no network requests when someone opens it. Remove anything from the starter template that would load from outside the file. The PitchKit data loaders fetch from GitHub, so we'll fetch the data once, save it in the project and bundle it into the page.

Write a short project brief to CLAUDE.md covering the goal, the match, the stack and the single-file rule, so the next session starts with it. Don't build anything else yet.
```

</Tab>

PitchKit is the charting library, and it's young enough that no model has learned it. Ask an agent
for a shot map without help and it tends to write mplsoccer's Python API in JSX, using components
that don't exist. `skills install` copies PitchKit's own instructions for agents into the project,
matched to the version you installed. Claude Code looks for them in `.claude/skills` and Codex in
`.agents/skills`, which is why the two prompts differ, along with the name of the brief file.

The single-file rule is in the first prompt because otherwise the agent builds the deck around a
live fetch. PitchKit's data loaders fetch from GitHub when the page opens, and a report that does
that breaks the moment someone opens it on a train. The skill's own data example fetches live, so
unless the prompt says otherwise, that's what the agent copies. The line about the starter template
is there because Vite's template links to a favicon and a few websites, and the agent found them
with a search for `http` in every run.

## 2. Build an empty scaffold

```text title="Prompt"
Now the empty scaffold: the deck, with no content in it yet. It should already look like a finished piece of analysis: minimal, clean, data first, in the PitchKit brand.

- Background #0a0a0a. Text #fafafa, secondary text #a3a3a3. System UI font, tabular numbers for every stat. Panels (like the key numbers and the takeaways) are #121212 with a 1px #262626 border and 12px radius.
- Spain in PitchKit's emerald #34d399, England in #38bdf8. Goals are #fb923c.
- Pitches: surface #0b1712, lines rgba(255,255,255,0.32), no stripes. Theme PitchKit through its CSS variables only, including the chart variables, so the axes, grid and labels read properly on a dark page.
- It's one scrolling page that works like a slide deck. Each slide is a full-screen section, at least the full width and height of the screen. Scrolling, the down arrow, space or Page Down snaps to the next slide, and the up arrow or Page Up goes back. The slide is the screen, so no frames or boxes around it. Add a small progress indicator at the edge, and a subtle "next" chevron on every slide but the last.
- On a phone (under 640px wide) the slides are still full width and a screen tall. A slide may run longer than the screen if it needs to, and no text is smaller than 14px (footnotes 12px).
- Every slide has a headline that states its main finding, a chart area, and a footer: "Built with PitchKit" and "Data: StatsBomb open data". No gradients, no shadows, no emoji.
- The page must also work inside an iframe on another page, with each slide filling the frame.

For now, put one slide in it: the headline "Spain v England" and an empty PitchKit pitch. Then build, open dist/index.html in a headless browser, screenshot it at 1280×720, 960×540 and 375px wide, and look at all three. Fix anything wrong before you stop.
```

  name="scaffold"

  caption="The scaffold: one slide, an empty pitch, and the PitchKit look."

Everything about the look goes in this prompt, before there's anything to look at. That way every
slide that follows comes out in the same style and you don't have a restyling pass at the end. Ask
for "clean" without saying what that means and the agent picks the colours, so the prompt gives it
hex values. These are PitchKit's. Use your club's if you like, as long as the two teams are easy to
tell apart and goals get a third colour neither team uses.

The layout is in there too. Each slide is one full screen and the page snaps from one to the next,
so it reads like a deck without any slide software. The phone rules are here for the same reason. A
slide built at 1280px and squeezed down later ends up with chart labels you can't read, so the
prompt sets a 14px floor and says what a slide does on a narrow screen.

The last line, about taking a screenshot and looking at it, is in every prompt from here on. The
first time through we asked only for a type check and a build. Both passed, and the passes row on
the page read 0, with a completion rate of NaN%. Here the screenshots caught that the pitch was
blank on a laptop, because a CSS sizing rule had collapsed it, and that the footer was in the wrong
place on a phone.

## 3. Get the data, and look at it

```text title="Prompt"
Now the data. Write scripts/fetch-match.ts using @pitchkit/data-providers/statsbomb to fetch the match record (competition 55, season 282), the lineups and the events for match 3943043. Save them to src/data/match.json. Keep every event that has a location, plus the substitutions, the cards and the lineups; drop the rest. Add it as an npm script and run it.

Then, without changing the deck, tell me what's in the data: the score, the goalscorers and their minutes, shots and xG per team, and any traps you noticed (periods, stoppage time, penalties, own goals, player names). Check these against the raw events rather than what you remember of the match.
```

Read this reply properly. You should get back:

|       | Spain                                  | England         |
| ----- | -------------------------------------- | --------------- |
| Goals | Nico Williams 47', Mikel Oyarzabal 86' | Cole Palmer 73' |
| Shots | 16                                     | 9               |
| xG    | 1.79                                   | 0.73            |

If your numbers are different, sort it out now. It's a lot easier than finding out from a finished
slide.

The agent has read plenty about this match, and the last line of the prompt is there to stop it
filling gaps from memory. Every run also flagged the same two traps. StatsBomb's minute is elapsed
time, so Williams scores at 46:09 on its clock and the broadcast says 47'. And the clock restarts at
45' for the second half, so the minutes 45 to 47 exist twice, once in first-half stoppage time and
again after the restart. An agent that sorts by minute alone can put Williams' goal in the wrong
half.

Players are listed under their full legal names, so without being told the agent will write
"Nicholas Williams Arthuer" on the title slide. The lineups carry a `player_nickname` for each
player, which is where "Nico Williams" comes from. England's players mostly have none, so those
names fall back to the registered ones. The data has no penalties, own goals or shootout, and the
agent said so.

What you ask it to keep here decides what it can count later, and this prompt has a flaw. "Every
event that has a location" sounds thorough, but the final whistle has no location, so it was
dropped. Nothing complained until step 10, when the check found the last-15-minutes window was a
minute out. It's on the list at the bottom of the post.

## 4. The first slides

```text title="Prompt"
Now the first slides. Every number must be calculated from src/data/match.json, including the numbers in headlines: write the sentences yourself, but don't type any figure into them, and don't make a claim the numbers don't show. Nothing from memory. For every figure, tell me in a line how you worked it out.

Replace the placeholder slide with:

1. A title slide: teams, score, scorers with minutes (use nicknames), competition, stage, date, venue. Its headline should be a sentence about the result, not the scoreline repeated.
2. Key numbers, side by side: goals, xG, shots, shots on target (a goal counts as on target), passes, pass completion, share of passes (each side's passes over both sides' passes; that's not possession).
3. An xG race chart across the match, with goals marked and the scorers labelled.

Then build, open dist/index.html in a headless browser, screenshot every slide at 1280×720 and at 375px wide, and look at them. Check every slide shows sensible numbers and nothing is cut off or blank. Fix anything wrong before you stop.
```

The rule about numbers does most of the work in this prompt. Agents like to type `2–1` into a
headline, and from memory that's usually right, which is why it goes unnoticed on the day it's
wrong. Making it calculate every figure, and say how, is how you find the choices it made without
telling you. StatsBomb has no possession figure, for example, so an agent asked for possession will
make up a formula. Share of passes is something we can count, so the prompt asks for that and the
footnote says it isn't possession. The title slide's headline is a sentence about the result because
an earlier run just repeated the scoreline under the big numbers.

The screenshots caught the race chart. The end labels came out garbled, because PitchKit's chart
colours default to a light theme and the skill doesn't list the variables, so on a dark page the
text gets a white halo. If you see that, it's why. England's scorer label also sat on its own line,
and on a phone two of the labels collided, so the agent wrote placement rules for each one.

## 5. Momentum

```text title="Prompt"
Add a match momentum slide after the xG race: bars for each minute, Spain up and England down, with goals and cards marked beneath. StatsBomb has no momentum figure, so derive one, and say in the slide's footnote that it's derived: for each minute, count each side's on-ball events (every event with a location and a player) in the attacking third, subtract England's from Spain's, and smooth over three minutes. Same rules on numbers, and the same build, screenshot and check as before.
```

<StageShot
  name="momentum"
  alt="Match momentum chart: green bars above the line for Spain and blue bars below for England, with goal and card markers underneath"
  caption="Slide 4, momentum. Derived from event data, not a StatsBomb figure."
/>

There's no agreed way to measure momentum, so a bare "add a momentum chart" gets whatever the agent
invents, and you'd have no way to know what the bars mean. The prompt gives it one line you can
defend: on-ball events in the attacking third, Spain minus England, smoothed. The footnote on the
slide repeats it, so the coach reading the report knows too.

Two details are easy to miss on this slide. The second half's bars restart at 45, so the bars for 45
to 47 appear in both halves. And "on-ball" is looser than it sounds. The prompt says every event
with a location and a player, and Pressure events have both but happen off the ball, so the agent
counted them. It followed the wording, and it's on the list at the bottom. The agent's first
headline here ran to four lines and squashed the chart, and it saw that in the screenshot.

## 6. Shots

```text title="Prompt"
Add a shots slide: a shot map for each team, cropped to the attacking half, side by side on a laptop and stacked on a phone. Marker size follows xG, goals are highlighted, and each shot has a tooltip with the player, minute and xG: on hover on a laptop, and on a tap on a phone (if the library's tooltip doesn't open on tap, add a tap fallback). Same rules on numbers, and the same build, screenshot and check as before.
```

<StageShot
  name="shots"
  alt="Two shot maps cropped to the attacking half: Spain's 16 shots clustered in and around the box, England's 9 more spread out, goals in orange"
  caption="Slide 5, shots."

On a laptop, hover over a shot and you get the player, minute and xG. A phone is trickier.
PitchKit's shot tooltip only listens for the mouse, and in the agent's tests it didn't open on a
tap, so it built its own tap readout, which shows the shot's details under the map. That's why the
prompt asks for a fallback. We've only tried it with emulated taps, not on a real phone. On a phone
the two maps stack, which the prompt also asks for.

```text title="Prompt"
Add two slides on how the match started and finished: the first 15 minutes, and the last 15 minutes up to the final whistle, stoppage time included. For each, show both teams' shots as maps, with the shots and xG for each team in that window. Say in a footnote how you defined the windows, and use the same minute clock as the rest of the deck. The headline of each slide should say what happened in that window. Same rules on numbers, and the same build, screenshot and check as before.
```

This is the part of a report a coach reads first. How did we start, and how did we finish? Spain had
both shots in the opening 15 minutes, worth 0.19 xG, and England had none, and the headline says so.
The last window has the winner.

"The last 15 minutes" can mean 76 to 90, or the last 15 up to the whistle. The prompt says up to the
whistle, stoppage time included, and asks for the window in a footnote so a reader can see which one
you got. If you want the other reading, say which. The first version of this window was a minute
out, for a reason you'll meet in step 10.

## 8. Pass networks

```text title="Prompt"
Add a pass networks slide, one pitch per team, for its starting XI up to that team's own first substitution. Each player sits at the average spot of their passes made and passes received (made means attempted, received means completed). Node size is passes made plus received, and lines join pairs with 3 or more completed passes between them. Label each node with a shirt number and a name, and make sure nothing overlaps or runs off the pitch, on a phone as well. Say in a footnote how long each team's window is. Same rules on numbers, and the same build, screenshot and check as before.
```

<StageShot
  name="passes"
  alt="Pass networks for Spain and England: circles at each starting player's average position, joined by lines, with shirt numbers and names"
  caption="Slide 8, pass networks. On a phone the two pitches stack, and the slide runs longer than the screen."
/>

This was one of the harder slides. Rodri went off injured at half-time, so Spain's window is the
first 47 minutes, while England's runs to Kane's substitution on 61', 63 minutes in. The two windows
aren't the same length, so the counts aren't comparable, and the footnote says that.

The first layout had labels without a place to go and pitches that were too small, and the agent
found that with a script that measured every label against every other label and circle. Two pairs
of players, Morata and Olmo for Spain and Foden and Mainoo for England, had almost the same average
position, so their circles were nudged apart and the footnote says so. The prompt says nothing may
overlap and also that each player sits at their average spot, which can't both be true, and the
agent settled it that way. On a phone the pitches turn vertical and stack, so the slide runs longer
than the screen.

If the plan or the code mentions a `<ShotMap>` or `<PassNetwork>` component, stop there. PitchKit
doesn't have either. A pass network is a pitch with arrows and a scatter layer on it, and seeing
those names means the agent didn't read the skill.

## 9. The takeaways

```text title="Prompt"
Add a last slide with three takeaways in plain English. Each one must be backed by a number from the deck, with a note of which slide it comes from, and must only claim what that number shows. No takeaway may rely on a number that only appears in a tooltip. Same rules on numbers, and the same build, screenshot and check as before.
```

<StageShot
  name="takeaways"
  alt="Three takeaway cards: 1.79 v 0.73 xG, the winner at 86', and 64.7% of passes, each with the slides it comes from"
  caption="Slide 9, the takeaways, with the slide each number comes from."
/>

The takeaways are where overclaiming creeps in, since they're the only slide that's all sentences.
Across the runs we saw "the goals didn't follow the chances", in a game won by the side with 2.5
times the xG, and "Spain had the ball", which is a claim about possession in a deck that only
measures passes. Another run's first wording was "none from a shot worth more than 0.28 xG". The
biggest goal was worth 0.283, so it was quietly false, and the agent caught it on its own re-read.

The slide-reference line makes the agent show its working. Each takeaway points back to the slides
it comes from, so anyone can check a claim against them. The prompt also says no takeaway may rely
on a number that only appears in a tooltip, because the run before broke that rule on its first try.

## 10. Check it before you send it

```text title="Prompt"
Review the deck as if you were the analyst about to send it. Rebuild, then:

- Write a separate script that re-derives every number in the deck from the raw StatsBomb events, without using the deck's code, and compares it with the built page, including chart labels and tooltips. List anything that doesn't match.
- Open dist/index.html in a headless browser with the network blocked and confirm it makes no requests and still renders every slide, at 1280×720, at 375px wide, and inside a 960×540 iframe, where every slide must fill the frame without being clipped.
- Read the headlines and takeaways again and confirm each one only claims what the numbers in the deck show.

Fix whatever is wrong, then give me the final file size and a one-paragraph summary I can paste into an email with the deck attached. Only quote figures the check confirmed.
```

The checking script mustn't share code with the deck, otherwise a bug in one can hide behind the
same bug in the other. This run's script downloaded the raw StatsBomb files fresh and ran 33 checks,
including every one of the 25 shot tooltips. It found a real bug. Step 3 had dropped every event
without a location, and the final whistle has none, so the data didn't know when the match ended.
The last-15-minutes window was a minute out at both ends. The agent kept the whistle events and
fixed the window, and the shots in it didn't change, which is why nothing on the slide looked wrong.

An earlier run's check found a different set of problems in the details nobody looks at. Tooltips
showed StatsBomb's raw outcome `Off T`, a takeaway cited a slide for a number you could only see by
hovering, and chart text was under the 14px floor. The words "including chart labels and tooltips"
are what found most of that. Without them the script would only read the text on the page.

The check also opens the deck inside a 960×540 frame, because this site shows the report in one. The
maps and networks need a bit more height than that, so four slides are taller than the frame and
scroll inside it. Legible maps and "without being clipped" pull against each other there, and the
prompt doesn't allow for it.

Read the headlines and takeaways yourself even after the check. They're the part a coach will quote
back to you.

## Sending it

`dist/index.html` is the deck, 2.1 MB. It has the data and the charts inside it, so it works without
an internet connection and anyone can open it in a browser.

Some company email systems block `.html` attachments, and a phone's attachment preview often won't
run the page's code, so the recipient sees a blank screen. Put the file in a shared drive or a Teams
or Slack channel, and tell people to download it and open it in Chrome, Safari or Edge. Do a test
send to yourself first.

## What I'd change next time

The prompts above are the ones we ran in the last run, word for word. Four things stand out:

- **Step 3: keep the final whistle.** Add "and the Half End events" to what it keeps.
- **Step 5: say what "on-ball" means.** "Every event with a location and a player" includes
  Pressure, which is off the ball.
- **Step 8: say what to do when nodes overlap.** "If two nodes would overlap, nudge them apart and
  say so in the footnote."
- **Step 10: allow taller slides.** "Slides may be taller than the frame if the maps need it."
